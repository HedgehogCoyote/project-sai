# SAI 구현·검증 정리와 다음 작업

정리일: 2026-10-11. 기준 커밋: `492ca51`.
후속 업데이트: 맵 서버 연동과 실제 HTTP 세션 검증을 완료했다. 아래는 연동 전 기준의 정리이며,
최신 동작·검증·남은 제한은 [맵 서버 연동](../architecture/room-server-sync.md)을 참고한다.
현재 소스와 기존 측정 산출물을 확인한 기록이다. 이 문서 작성 중 테스트를 다시 실행하지 않았다.
아래 작업 시간은 개발자 1명 기준 순수 작업 시간의 추정이며 승인 대기·운영 배포는 제외한다.

## 1. 이번에 완료한 기능

| 기능 | 구현 내용 | 현재 한계 | push한 커밋 |
| --- | --- | --- | --- |
| 공간 맵 JSON 저장 | 공간별 JSONB 저장·조회, 배치 검증, 권한 검사, 버전 충돌 409, 동시 저장 제어 | 백엔드만 구현. 방 편집 화면은 아직 localStorage 사용 | [22512f5](https://github.com/HedgehogCoyote/project-sai/commit/22512f5) |
| 사용자 검색·초대 | 아이디 검색, 이름·아이디 표시, 대상 선택, 실제 userId로 초대, 본인 차단, 이전 요청 취소, 오류·재시도, 중복 전송 차단 | 기존 검색 API 연결. 검색 결과가 참여 가능 여부를 보장하지 않음 | [df08df3](https://github.com/HedgehogCoyote/project-sai/commit/df08df3) |
| 검색 성능 실험 | 1만·10만·100만 명 합성 데이터, 8개 검색 조건, 4가지 방식, 원시 측정·실행 계획 저장 | JDBC 실험. HTTP/JPA·동시 접속 성능은 미측정. 제품 쿼리·인덱스 미변경 | [492ca51](https://github.com/HedgehogCoyote/project-sai/commit/492ca51) |

세 커밋은 `origin/main`에 push했고 당시 로컬 HEAD와 원격 SHA가 일치했다.
활동·할 일·기록 등 내부 콘텐츠도 아직 브라우저 로컬 저장이다. 서버에 맵 JSON이 저장된다고 콘텐츠까지 공유되는 것은 아니다.

## 2. 검증 결과와 증거 범위

- 백엔드 테스트 57개 통과: 실제 PostgreSQL을 사용한 맵 저장·권한·잘못된 요청·버전 충돌·동시 저장 검증 포함.
- 프런트 단위 테스트 18개, Chromium E2E 34개 통과. 타입 검사·빌드 통과.
- 프런트 E2E와 구현 화면 캡처는 모의 API를 사용했다. 실제 서버와 연결한 검색→초대→수락의 전체 흐름은 추가 검증이 필요하다.
- 성능 실험 96개 측정 조건 완료. 각 조건 워밍업 5회 후 30회 측정. 방식별 결과 ID·순서 일치와 최대 10명 반환을 확인했다.
- 실험용 데이터·스키마·인덱스는 트랜잭션을 롤백했다. 제품 데이터에 합성 사용자를 넣지 않았다.

## 3. 검색 성능은 얼마나 달랐나

100만 명 합성 데이터에서 측정한 JDBC 쿼리 p95다. 실제 API 응답 시간이 아니다.

| 검색 | 기존 전체 컬럼 | 필요한 3개 컬럼 | 3개 컬럼 + GIN 기본 계획 | 3개 컬럼 + GIN 검색어별 계획 |
| --- | ---: | ---: | ---: | ---: |
| 희귀 긴 문자열 | 935.125ms | 940.502ms | 922.097ms | 2.065ms |
| 결과 없음 | 894.107ms | 894.850ms | 898.181ms | 0.444ms |
| 3자 검색 | 14.183ms | 13.873ms | 11.759ms | 14.553ms |
| 2자 검색 | 0.952ms | 0.926ms | 1.069ms | 0.925ms |
| 흔한 문자열 | 0.845ms | 0.875ms | 0.823ms | 0.770ms |

필드 수를 7개에서 3개로 줄여도 전체 행을 검사하는 비용은 남았다.
GIN 인덱스가 있어도 재사용된 generic 계획이 기존 B-tree를 선택하는 사례를 확인했다.
검색어별 계획을 선택한 후보는 희귀 긴 문자열에서 약 99.78% 빨라졌지만, 3자 검색은 약 2.61% 느렸다.
따라서 모든 3자 이상 조건에서 p95 30% 개선이라는 실험 목표는 충족하지 못했다.

100만 명의 GIN 인덱스는 약 71.6MiB, 생성 시간은 약 6.3초였다.
1000행 삽입 단일 관측은 12.8→25.5ms였다. 이는 반복 측정한 쓰기 p95가 아니므로 안정적인 비용 증가율로 단정하지 않는다.
임시 테이블·워밍업된 캐시·합성 데이터·단일 클라이언트 조건이며, 작은 차이는 재측정이 필요하다.
현재 증거로 제품에 GIN이나 force_custom_plan을 일괄 적용하기는 이르다.

[전체 성능 보고서와 재현 방법](../benchmarks/user-search/README.md)

## 4. 다음 작업 우선순위

추천 순서: **맵 서버 연동 → 실제 서버 전체 흐름 검증 → 검색 조회 개선 → 활동·할 일 서버화**.
공간을 중심으로 사용자를 초대하고 기능을 연결하는 흐름에서, 구성원이 같은 배치를 보는 기반을 먼저 완성한다.

| 순서 | 작업 | 예상 시간 | 완료 기준 |
| --- | --- | --- | --- |
| 1 | 방 화면과 맵 API 연결, 저장 상태·권한·충돌 처리 | 12~20시간 | 저장 후 새로고침·다른 멤버 계정에서 같은 배치 조회. MEMBER 편집 차단. 실패·409 시 초안 유지 |
| 2 | 실제 백엔드 기반 검색·초대·수락·맵 공유 E2E | 4~8시간 | 독립 테스트 계정 두 개로 검색→초대→수락→공간 진입→맵 조회 완료. 테스트 데이터 정리 |
| 3 | 검색 DTO projection + 서버 trim 후 길이 검증 | 3~6시간 | 검색 의미·정렬·10명 제한 유지. SQL에서 필요한 3개 필드만 조회. 공백·특수문자 검증 |
| 4 | 실제 API 검색 성능과 쓰기 비용 재측정 | 6~12시간 | HTTP p50/p95·오류율, 실제 Hibernate SQL·준비된 쿼리 계획, 반복 삽입 p95, 동시 요청 결과 확보 |
| 5 | 활동·할 일의 서버 저장 최소 기능 | 20~36시간 | 다른 멤버 계정에서 같은 활동·할 일 조회. 공간 권한·활동 ID·수정 충돌 검사 |

1번 추정에는 최소 범위의 데이터 보존 정책·시안·연동·검증을 포함한다.
기존 로컬 데이터의 완전한 이관이나 서버 활동 ID 도입까지 포함하면 범위와 시간을 다시 잡아야 한다.
5번은 활동·할 일만 대상으로 하며 기록·일정·정산·투표 등 전체 콘텐츠 서버화는 별도 작업이다.

## 5. 가장 먼저 할 맵 서버 연동의 설계 항목

### 데이터 계약

- 현재 화면의 Furniture는 `w`, `h`, 선택적 `event`를 갖지만 서버 요소에는 이 필드가 없다.
- 크기 `w/h`는 가구 종류·회전으로 복원하고 PUT에는 서버가 받는 필드만 보낸다.
- `event`는 브라우저 로컬 활동 ID다. 서버는 아직 이를 이해하지 못한다. 임의로 제거하거나 공유 가능한 ID처럼 취급하지 않는다.
- 활동 연결 보존 방식을 먼저 정한다. 최소 연동 범위에서는 공용 배치와 로컬 활동 연결을 분리하는 안을 검토하고, 다른 계정에서 해당 활동이 없을 때의 동작도 시안에 표시한다.
- 낮/저녁 개인 설정은 계속 로컬 설정으로 취급한다.

### 조회·저장과 권한

- 공간 진입 시 GET으로 서버 배치·버전을 가져온다. 로딩 중 잘못된 초기 배치를 편집·저장하지 못하게 한다.
- 미저장 `version: 0`과 이미 저장된 빈 배치를 구분한다. 빈 배열을 기본 가구로 덮어쓰지 않는다.
- OWNER/MANAGER만 저장하고 MEMBER는 조회한다. 권한 변경 뒤의 서버 403도 처리한다.
- 저장은 편집 완료 버튼으로 전체 JSON을 PUT한다. 성공한 서버 응답으로 배치와 버전을 갱신한다.
- 저장 실패에는 초안을 유지한다. 중복 저장과 공간 전환 뒤의 이전 응답 반영을 차단한다.

### 충돌·기존 로컬 데이터

- 409에는 초안을 보존하고 최신 서버 배치를 확인할 수 있게 한다. 최신 버전으로 자동 재시도해 다른 변경을 덮어쓰지 않는다.
- 기존 브라우저 배치는 자동 업로드하지 않는다. 명시적 가져오기와 원본 보존 정책을 정한다.
- 서버에 배치가 이미 있거나 다른 멤버가 동시에 최초 저장했을 때도 버전 검사를 적용한다.
- 손상된 로컬 JSON과 지원하지 않는 연결 정보는 이유를 표시하고 원본을 남긴다.
- 첫 연동은 저장·재조회 기반이다. 실시간 동시 편집은 구현 범위에 포함하지 않는다.

### 시안·검증에서 보여줄 것

다음은 제안 범위이며 아직 구현 승인이 아니다. 프로젝트 규칙에 따라 실제 PNG 시안과 아래 검증안을 제시한 뒤 승인된 범위만 구현한다.

| 시나리오 | 통과 기준 | 남길 증거 |
| --- | --- | --- |
| 저장 후 재진입 | 배치·회전·라벨·버전 일치 | API 응답 및 실제 화면 캡처 |
| 두 멤버의 조회 | 같은 공간의 서버 배치 일치 | 서로 다른 계정의 화면 및 E2E 결과 |
| MEMBER 편집 시도 | 화면에서 편집 차단, 직접 PUT은 403 | 권한 화면·통합 테스트 |
| 같은 버전 동시 저장 | 하나 성공, 하나 409. 실패한 화면의 초안 보존 | 두 브라우저 E2E 및 최종 DB 값 |
| 네트워크 실패·401·403 | 실패를 표시하고 초안 손실 없음 | 오류 시나리오 E2E |
| 빈 배치·로컬 가져오기 | 빈 배치 유지, 승인 없는 업로드 없음, 원본 보존 | 가져오기 전후 데이터와 E2E |
| 활동 연결·공간 전환 | 연결 정보 조용히 삭제하지 않음. 이전 공간 응답이 현재 화면을 변경하지 않음 | 변환 단위 테스트·화면 E2E |

## 6. 후속 고도화

- 서버 저장 기반이 안정된 뒤 SSE/WebSocket으로 변경 알림을 검토한다. 자동 병합·실시간 편집은 별도 동시성 설계가 필요하다.
- 내부 콘텐츠는 활동·할 일부터 작은 단위로 서버화하고, 실제 공간 멤버와 콘텐츠 담당자의 식별자를 연결한다.
- 검색은 실제 API 측정에 따라 인덱스·계획 선택을 결정한다. 접두 검색 전환은 결과 의미가 달라지므로 별도 정책 결정이다.
- AI 추천·기능 생성은 이후 확장 후보이며 현재 구현된 기능으로 설명하지 않는다.
