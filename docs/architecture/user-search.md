# 사용자 검색과 초대

2026-10-11: 승인한 검색·선택 시안을 기존 초대 화면에 반영했다.

## 현재 동작

`UserInvitation.vue`가 기존 `GET /api/users/search?loginId=...`를 호출한다.
앞뒤 공백을 제거한 2~20자 검색어로 버튼/Enter를 눌렀을 때만 요청하며 입력마다 자동 검색하지 않는다.
서버는 아이디 부분 일치·대소문자 무시 검색을 하고 아이디 순으로 최대 10명을 반환한다.
결과에는 이름과 아이디를 보여주고 한 명을 선택하면 반환된 실제 `userId`로 기존 초대 API를 호출한다.

- 본인 결과는 표시하되 선택을 차단한다.
- 검색어가 바뀌거나 공간/화면이 바뀌면 AbortController로 검색을 취소한다. 요청 번호와 공간 ID도 검사해 이전 응답이 최신 상태를 변경하지 못하게 한다.
- 검색 전/중/결과 없음/오류와 재시도를 제공한다.
- 초대 중 입력·선택·중복 전송을 차단한다. 성공 후 선택을 해제하고 실패 시 선택을 유지한다.
- 401 응답은 기존 HomeView 인증 만료 처리로 전달한다.
- 이미 참여한 사용자/중복 초대 여부는 초대 시 서버가 판단한다. 검색 결과는 참여 가능 여부를 보장하지 않는다.
- 캐시와 서버 쿼리·인덱스 변경은 이번 구현에 포함하지 않았다. fetch 취소가 이미 실행 중인 서버 SQL의 취소를 보장하지는 않는다.

캡처와 Chromium E2E는 모의 API 응답을 사용한다. 실제 백엔드와 DB를 연결한 전체 흐름의 증거는 아니다.
`user-search.spec.ts`는 검색어 공백·인코딩, 명시적 요청, 본인 차단, 대상 ID 전달, 실패·재시도,
검색 취소·공간 전환·세션 만료, 전송 중 잠금과 데스크톱/모바일 입력 폭을 검증한다.

시안과의 차이: 기존 공간 상단 전환·탭·체험 데이터 안내를 유지했고 선택은 접근 가능한 실제 라디오 버튼으로 표현했다.

## 서버 최적화 후보와 검증안

다음 후보는 제품에는 미적용이다. 독립 PostgreSQL 실험의 측정 결과와 실행 계획은
[사용자 검색 성능 비교](../benchmarks/user-search/README.md)에 기록했다.
이 실험은 JDBC 쿼리 시간 비교이며 실제 HTTP API p50/p95와 반복 삽입 p95는 아직 측정하지 않았다.

1. **필요한 필드만 조회:** 현재 `UserService`는 User 엔티티를 읽은 뒤 userId/loginId/name으로 변환한다.
   DTO projection으로 이 세 필드만 조회하면 비밀번호 해시·연락처 등 불필요한 컬럼을 읽지 않아도 된다.
2. **부분 검색용 인덱스:** 기존 `login_id` UNIQUE B-tree는 중간 문자열 검색의 효율을 보장하지 않는다.
   실제 Hibernate SQL의 대소문자 변환식과 일치하는 `pg_trgm` GIN 인덱스를 후보로 비교한다.
   2자 검색처럼 추출할 trigram이 없는 패턴은 인덱스 효과가 제한될 수 있다.
   정확/접두 검색으로 정책을 바꾸면 결과 의미가 달라지므로 별도 결정이 필요하다.
3. **정규화와 제한:** 현재 백엔드는 요청 길이를 검증한 뒤 trim한다. 서버에서도 trim 후 최소 길이를 검증하는 보완을 고려한다.
   실제 트래픽을 본 뒤 사용자별 요청 빈도 제한을 결정한다. 자동완성을 도입한다면 debounce와 취소를 함께 사용한다.

검증 데이터는 임시 스키마에 생성한 합성 사용자 1만·10만·100만 명이다.
2자/3자/긴 검색어, 흔한 문자열/희귀 문자열/결과 없음, 대소문자, `%`·`_` 리터럴을 비교한다.
동일한 조건에서 워밍업 후 반복 실행해 SQL 실행 계획(`EXPLAIN (ANALYZE, BUFFERS)`), 읽은 컬럼,
버퍼 접근 수, API p50/p95, 인덱스 크기·사용자 삽입 비용을 기록한다.

필수 통과 기준은 결과·순서·10명 제한 유지와 ID/이름/아이디 외 컬럼 미조회다.
인덱스 채택 목표는 10만·100만 명의 3자 이상 검색에서 p95 30% 이상 개선이며,
2자·흔한 검색어와 삽입의 p95가 10% 넘게 악화되면 채택을 재검토한다. 수치는 검증 전 목표이며 측정 결과가 아니다.

참고: [PostgreSQL 인덱스 종류](https://www.postgresql.org/docs/16/indexes-types.html),
[pg_trgm 인덱스 지원과 짧은 패턴의 한계](https://www.postgresql.org/docs/16/pgtrgm.html).
