# 받은 초대함 시안과 구현 제안

2026-10-11. 현재 API와 HomeView 스타일을 확인해 만든 구현 전 시안이다.
애플리케이션 소스·API는 변경하지 않았다. 예시 데이터와 시안 버튼의 화면 전환은 서버에 연결되지 않는다.

## 시안

- desktop.png: 대기 중 초대 목록, 헤더 받은 초대 진입점과 배지.
- deny-confirmation.png: 공간·초대한 사람을 확인하고 거절하는 확인 창.
- accepted.png: 수락 후 초대함을 유지하며 공간으로 이동하는 버튼 제공.
- history.png: 수락·거절 완료 목록. 수락된 공간도 내 공간 목록에서 실제 참여가 확인돼야 이동 버튼을 제공한다.
- states.png: 빈 목록·조회 실패·처리 중·결과 불명·부분 성공·상태 변경·중복 공간 초대.
- mobile.png: 390px에서 카드 액션을 별도 줄로 배치한 시안. 가로 넘침 검사 통과.

## 진입과 화면 구조

1. 로그인한 화면의 헤더에 ‘받은 초대’를 추가한다. 배지는 GET 결과의 PENDING 개수이며 조회 전·실패에는 0으로 단정하지 않는다.
2. 계정 전체 초대함은 `/spaces?panel=invitations`를 제안한다. 기존 공간의 `view=invite`(초대 보내기)와 구분한다.
3. 기존 미저장 맵·콘텐츠 이탈 확인을 유지한다. 초대 처리 중에는 초대함 새로고침·다른 처리·내비게이션·로그아웃을 잠근다.
4. 기본 탭은 대기 중. 처리 완료 탭은 ACCEPTED/DENIED를 표시한다. 일단 API 배열 순서를 유지한다. 초대 날짜는 표시하지 않는다.
5. 일반 수락은 명확한 버튼으로 바로 처리한다. 거절만 별도 확인 창에서 공간·초대한 사람을 다시 보여준다.
6. 수락 후 목록을 갱신하고 초대함에 성공 안내와 공간 이동을 제공한다. 자동 이동하지 않는다.
7. 공간에 이미 참여 중인 다른 PENDING 초대에는 수락 대신 공간 이동과 이 초대 거절을 제공한다. 거절은 기존 멤버 자격을 삭제하는 동작이 아니다.

## 기존 API 계약

| 기능 | 요청 | 응답 사용 |
| --- | --- | --- |
| 받은 초대 조회 | GET `/api/invitations/received` | invitationId, spaceId, spaceName, inviterName, invitationStatus |
| 수락 | POST `/api/invitations/join` `{ invitationId }` | 반환값은 spaceMemberId. 이동 대상은 초대의 spaceId를 사용 |
| 거절 | POST `/api/invitations/deny` `{ invitationId }` | 거절 처리 후 받은 초대 목록 갱신 |
| 참여 공간 갱신 | GET `/api/spaces/my` | 수락 뒤 실제 참여 공간·역할 확인, 공간 이동 |

기존 InvitationResponse에는 초대 일시·공간 인원·공간 썸네일·초대한 사람의 loginId가 없다.
시안은 공간 이름·초대한 사람의 이름·상태만 사용한다. 원형 그림은 장식이며 실제 공간 미리보기가 아니다.
수락 시 MEMBER가 되는 정책은 서버의 현재 동작이다. 상태는 PENDING/ACCEPTED/DENIED이며 만료 상태를 추가하지 않는다.
백엔드 API·초대 권한·정책·페이지네이션·실시간 알림 변경은 이번 제안 범위에 포함하지 않는다.

## 실패·경합 처리

- 조회 중·빈 결과·조회 실패를 구분한다. 탭별 빈 결과도 구분한다.
- 처리 요청은 한 번만 보내고 모든 초대 처리 액션을 잠근다. 요청 번호·계정·unmount 검사로 이전 응답 반영을 차단한다.
- 네트워크 실패로 처리 결과가 불명확하면 받은 초대와 참여 공간을 다시 조회한다. 새 상태를 확인하기 전 자동 재전송하지 않는다.
- 이미 처리됐거나 다른 탭에서 상태가 바뀌었으면 서버 오류를 표시하고 최신 목록을 확인한다. 재조회에도 실패하면 결과 불명 상태를 유지한다.
- 수락/거절 성공과 후속 GET 실패를 구분한다. 성공한 POST를 다시 보내지 않고 필요한 조회만 재시도한다.
- 수락 성공 뒤 spaces/my 실패에는 ‘공간 참여는 완료됨’을 표시한다. 공간 이동은 실제 공간 목록 확인 뒤 제공한다.
- 401은 기존 인증 만료 처리와 로그인 redirect를 사용한다. 서버 정책 오류는 해당 초대에 표시한다.
- API 응답의 이름·공간 제목은 텍스트로 렌더링한다. ID와 상태가 유효하지 않으면 처리 버튼을 활성화하지 않는다.

## 승인 후 검증 계획

| 시나리오 | 통과 기준 | 증거 |
| --- | --- | --- |
| 목록·배지·탭 | PENDING 개수 일치. 처리 상태에 맞는 탭·액션. 미조회/실패를 0건으로 표시하지 않음 | 모의 API E2E |
| 수락 | 올바른 invitationId로 POST 1회. 공간·초대 갱신. 기존 공간 유지, 명시적 공간 이동 | 요청 감시 E2E |
| 거절 | 확인 창의 공간·초대한 사람 일치. 취소에는 POST 없음. 확인 후 목록 이동 | E2E |
| 처리 중·이탈 | 중복 처리·새로고침·다른 초대·이동 잠금. 기존 미저장 맵 이탈 확인 유지 | E2E |
| 오류·부분 성공 | 조회/처리/후속 조회 오류 구분. POST 자동 재전송 없음. 초대 상태 확인 뒤만 액션 재활성화 | E2E |
| 다른 초대로 이미 참여 | 새 수락 요청 없음. 공간 이동·현재 초대 거절만 제공 | E2E |
| 계정·공간 전환·401 | 이전 응답 미반영, 상태 초기화, 로그인 경로 보존 | E2E |
| 실제 서버 두 계정 | 검색→초대→받은 목록→수락→공간 입장→맵 조회. 거절 후 상태 확인 | 실제 브라우저/API 결과를 구분해 기록 |
| 화면 | 데스크톱·390px 가로 넘침 없음, 키보드로 확인 창 접근·취소·복귀 가능 | 실제 구현 캡처·E2E |

수락 후 공간에 참여하는 것과 활동·도구 콘텐츠의 서버 공유는 별개다. 기존 로컬 콘텐츠 경계를 안내한다.
구현 시 타입 검사·빌드·관련 테스트를 실행하고 실제 구현 화면과 시안 차이를 기록한다.
예상 6~10시간은 프런트 연동·오류 처리·모의 API 검증 기준 추정이며, 실제 서버 브라우저 통합 환경 구축은 별도로 산정한다.
